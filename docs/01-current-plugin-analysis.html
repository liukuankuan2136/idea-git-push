现有 VS Code 插件分析

分析对象为 D:\code\my-workspace\git-push 当前源码，版本 0.3.12。重点不是复述 README，而是从实际代码还原功能边界、业务规则、数据流、失败语义和迁移风险。

1. 范围与结论

总体结论：具备完整迁移条件。业务能力主要由 HTTP、Git CLI、静态规则和本地状态组成，不依赖 VS Code 编辑器模型。需要重写的是平台接入层和交互层，核心规则可以等价迁移。

当前插件实际已发展为一个内部 DevOps 工作台，包含代码提交、工作项关联、工时管理、任务创建、日报和区域合规检查。若只按 README 中最初的“提交 + 推送 + 工时”实现 IDEA 版，会遗漏 0.3.7–0.3.12 的大量能力。

本分析把“功能一样”定义为：业务输入、DevOps 请求、Git 结果、工时计算、任务模板、区域规则及异常结果保持等价；交互步骤不要求一致，IDEA 版应主动合并为单弹窗。

3. 当前架构

VS Code 入口层：命令注册、通知、进度、浏览器/剪贴板、ExtensionContext。
Flow 交互层：QuickPickFlow、DailyTaskFlow、PushDayWorkFlow、RegionCheckFlow、TaskTemplateFlow。
业务与策略层：commit 模板、工时追加/覆盖、任务类型映射、区域合规规则、Git 恢复策略。
DevOps 接入层：CompanyDevOpsAdapter、会话 Cookie、pageId、响应解析、字段映射。
基础设施：Node fetch、child_process 调 Git、SecretStorage、globalState、OutputChannel。

当前优点

  • 已经抽象出 DevOpsProvider 接口，领域模型与供应商适配器基本分离。
  • commit 格式化、区域规则、缓存、映射存储均有独立文件，便于迁移。
  • 推送失败时具备 soft reset 恢复意识，能避免部分本地数据损失。
  • API 的多个 pageId、两阶段任务查询、非标准 JSON 等踩坑已沉淀在代码中。

当前耦合点

  • extension.ts 同时处理 UI、Git、事务和错误展示。
  • Flow 直接访问 VS Code API，无法脱离 UI 做流程测试。
  • 部分日期、默认值和映射散落在多个文件，存在行为不一致风险。
  • HTTP 解析使用 JavaScript Function() 执行响应，迁移到 Java 21 时不能原样复用。

关联工作项能力

  • 工作项类型：Task / Bug。
  • 默认加载当前登录用户的未完成项，并按产品分组。
  • 支持按编号手动查询，不受任务所属人员限制。
  • 展示预计工时、已发生工时、当前完成度和今日已有工时。
  • 工时类型含 “AI” 时，commit 参数由 -h: 自动切为 -aih:。

创建 Task 能力

  • 研发项目 → 产品 → 产品版本级联；标题尝试自动匹配区域；区域再级联实施项目。
  • 工时类型自动映射到任务类型，映射表包含 45 组代码，未命中回退任务类型 3。
  • 完成度低于 100% 时必须填写预计结束日期；预计工时按“含首尾日历天数 × 8h”计算。
  • 任务内容支持简易、普通、标杆三种模式，标杆模式覆盖 11 个章节并生成 HTML。
  • 运维命令使用 Git origin 记忆项目/产品；日常任务使用工作区路径记忆。

5. 核心流程

5.1 已有 commit 重写并推送

选择仓库
→
检查 upstream / 未推送 commit
→
收集 DevOps 元数据
→
amend 最新 commit
→
push
→
新增或更新工时

push 失败会执行 git reset --soft HEAD@{1} 尝试恢复 amend 前状态；push 成功后工时失败则无法撤回远端提交。

5.2 新建 commit 并推送

检查 staged changes
→
收集 DevOps 元数据
→
git commit
→
push
→
新增或更新工时

push 失败会执行 git reset --soft HEAD~1，将提交恢复为暂存改动。

5.3 运维工时补录

收集任务和 Git 信息
→
创建 DevOps Task
→
git commit
→
push（失败不阻断）
→
登记工时

该流程与普通提交的失败语义不同：任务一旦创建不回滚；push 失败也继续登记工时，并提示手动 push。

5.4 日常任务登记

不依赖 Git。按工作区路径预填项目/产品，创建 Task 后登记所选工时类型。工时登记失败不会删除已创建的 Task。

5.5 区域检查

选择研发项目和产品，查询本周全部状态、全部用户的 Task；逐项拉取工时后，将任务标题和工时内容合并做静态地名检查。规则 A 检查区域维度，规则 B 检查实施项目主地点。当前报告写入 VS Code OutputChannel。

6. 关键业务规则

6.1 commit message

${COMMIT_TYPE}:${SUBJECT} scrum -e ${CODE} -h:${HOURS} -s:${PROGRESS}

必需变量为 ${COMMIT_TYPE}、${SUBJECT}、${CODE}、${HOURS}、${PROGRESS}；另支持 ${TYPE}、${PROJECT}。Merge 会从 Merge: 修正为 Merge 。

合法类型：feat、fix、perf、refactor、test、style、build、chore、upd、doc、Merge。最终消息要求 10–500 字符，包含小写指令 scrum -e。

6.2 工时和完成度

字段appendoverwrite默认
工时今日已有工时 + 本次输入用本次输入替换append
工作描述已有内容 + 换行 + • subject仅 • subjectappend
完成度已有百分比 + 本次输入，上限 100%用本次输入替换overwrite

6.3 区域规则

  • “共同区域”任务的标题和工时内容不得出现任何地名。
  • 指定省份的任务不得出现其他省份或其城市。
  • 实施项目名称提取出的主地点不得与文本中其他地点冲突。
  • 省份修饰同省城市视为合法，例如“广西柳州”。
  • 比较时归一化“市/省”后缀，地名按长度优先匹配，避免短名称误命中。

用户名和 password 密文分别保存在 VS Code SecretStorage；普通设置、仓库映射、工作区映射和最后版本号不属于敏感信息。DevOps 会话 Cookie 只保存在运行期内存。

“清除缓存”不等于“退出登录”。当前命令不会删除 SecretStorage 中的用户名和 password 密文，但会清掉版本记录以及两类项目映射。IDEA 版应在 UI 上把“清缓存”“清映射”“删除账号”拆开表达。

8. DevOps API 特征

服务根地址固定为 https://devops.ctjsoft.com。认证通过 POST /login，请求为 FormData，字段含 username、password、loginType=password；响应需提取 Set-Cookie 和 userId。

模块pageId主要能力
部门工作项 / 工时h7BdNkJ任务查询、按编号查询、工时列表、新增/修改工时、工时类型
研发任务创建AbY8d4R研发项目、产品、区域、实施项目、版本、模块、人员、创建 Task
日报wlrFlaF今日工作、明日计划、工时校验、逾期任务、提交日报

任务分组查询存在两阶段协议：第一次拿分组摘要，第二次带 parentId、groupFieldValue 等展开具体任务。progressStatus="" 表示全部状态。

非标准响应是迁移的首要技术风险。部分端点返回包含 JavaScript IIFE 的对象字面量，而不是 JSON。现有实现以 Function() 执行整个响应。Java 21 已无内置 Nashorn，IDEA 版必须提供受约束的兼容解析器，不能假设所有响应都是标准 JSON。

场景成功顺序失败恢复不可逆点

commit + pushcommit → push → 工时push 失败 soft reset HEAD~1push 成功后无法自动撤远端

无 upstream 时：列出 remotes；单 remote 自动选择，多 remote 让用户选择；远程分支默认本地分支，随后执行 set-upstream push。已有 upstream 时直接 push。

10. 当前 UI 问题分析

步骤过多

关联任务流程通常需要 7 次左右 QuickPick/InputBox；创建 Task 在标杆模式下可能超过 20 次交互。用户无法一次看到完整输入，也难以返回修改前面的字段。

动作文字与模式不一致

元数据确认按钮固定写“确认并推送”，即使调用的是“仅提交”命令。任务模板标题也固定包含“运维工时补录”，日常任务场景中不够准确。

上下文被拆散

今日已有工时、项目/产品、任务信息、commit 预览分散在不同浮层。最终确认只有文本拼接，无法就地定位错误字段。

结果依赖输出面板

区域检查结果主要写到 OutputChannel。对于表格化筛选、复制问题项、打开任务详情并不友好。

配置与账号割裂

账号初始化通过命令完成，其他设置在 Settings。缺乏一个统一页面展示账号状态、测试连接、清缓存、清映射与诊断日志。

11. 已识别风险与缺口

级别问题影响IDEA 设计处理
高非标准 JavaScript 响应依赖 Function()Kotlin/JVM 无法直接解析；执行服务端脚本有安全风险JSON 优先；仅固定域名/固定端点启用受限兼容解析；限制体积、超时与可执行语法，并测试真实样本
高多系统副作用不具备原子性可能出现代码已推送但工时失败，或 Task 已建但 commit 失败显式步骤状态、幂等重试入口、失败结果摘要；不承诺伪事务
中多数日期使用 UTC toISOString()Asia/Shanghai 00:00–07:59 可能登记到前一天统一 ZoneId.of("Asia/Shanghai")
中getTasks() 每次请求，tasks Map 未读取配置名宣称任务缓存但实际未命中明确任务列表默认实时，手动刷新；字典类按 TTL 缓存
中已有仓库映射后选择“重新选择”不会覆盖旧映射下次仍出现旧项目/产品确认提交时始终更新当前映射
中运维补录所选工时类型用于 commit，但登记工时时强制寻找“代码编写”界面选择与实际登记类型可能不一致作为待确认行为，建议改为登记所选类型
中简易模式仍把未询问章节写入默认占位文案Task 内容可能冗长且含指导语建议简易模式仅写真实输入章节；保留兼容开关
低区域检查强制诊断日志日志较多，可能包含内部任务信息结果表默认；详细请求日志仅 debug 开启且脱敏
低README 的“三种推送模式”实际列出四行用户文档与实现轻微不一致IDEA 使用文档按功能矩阵生成

12. 迁移判断

模块迁移方式难度说明
领域模型、commit 格式按类型等价重写低纯数据与字符串规则
工时计算、任务类型映射纯函数迁移并补测试低适合参数化测试
区域地名字典与规则机械转换 + golden tests中数据量大但逻辑稳定
DevOps 标准 JSON APIOkHttp/JDK HttpClient + Jackson/kotlinx serialization中需保持 header、FormData、Cookie、pageId
非标准响应新增兼容解析层高必须基于真实响应样本验证
GitGit4Idea 发现仓库 + 受控 Git CLI 执行中保持命令语义，减少使用内部 API 风险
SecretStorage/globalStatePasswordSafe + PersistentStateComponent低平台有标准替代
多步骤 UI重新设计单弹窗，而非逐 API 翻译高涉及异步级联、状态、校验和结果反馈
推荐实现边界。首期完整覆盖 F01–F09；F10 不复刻 VS Code 的“比较本地版本再跳 GitHub”，而是优先采用 IDEA 标准插件更新机制。平台相关行为改变，但用户目标和最终能力更一致。
